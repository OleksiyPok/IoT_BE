# IoT Backend

[English](README.en.md) | [Українська](README.uk.md)

FastAPI-бекенд для отримання телеметрії ESP32 та записів подій з Amazon DynamoDB і надсилання команд світлодіоду через AWS IoT Core.

- **Документація API:** `http://127.0.0.1:8000/docs`
- **Схема OpenAPI:** `http://127.0.0.1:8000/openapi.json`
- **Вебсторінка керування LED:** `http://127.0.0.1:8000/`
- **Перевірка доступності API:** `http://127.0.0.1:8000/test/health`

## 1. Вимоги

- Python 3.10 або новіший.
- Обліковий запис AWS і доступ до ресурсів AWS, які використовує проєкт.
- Облікові дані AWS з дозволами, описаними в розділі [Налаштування AWS і дозволи](#4-налаштування-aws-і-дозволи).
- Таблиці DynamoDB і топік AWS IoT Core, які використовує пристрій, мають існувати та відповідати конфігурації нижче.

## 2. Запуск на іншому комп’ютері

Виконуйте всі команди з кореневої директорії бекенду — тієї, де розташовані `app/` і `.env.example`.

### Windows PowerShell

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install fastapi uvicorn boto3 python-dotenv
Copy-Item .env.example .env
```

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install fastapi uvicorn boto3 python-dotenv
cp .env.example .env
```

Відредагуйте `.env` за інструкціями наступного розділу, а потім запустіть API:

```bash
uvicorn app.main:app --reload
```

Відкрийте `http://127.0.0.1:8000/docs`, щоб переглядати й викликати ендпоїнти.

Для зупинки сервера натисніть `Ctrl+C`.

> У наданому архіві немає заповненого `requirements.txt`. Наведені команди встановлюють прямі Python-залежності, які використовує застосунок. Для відтворюваного встановлення підтримуйте `requirements.txt` із зафіксованими версіями пакетів.

## 3. Налаштування змінних середовища

Створіть `.env` на основі `.env.example` і налаштуйте його для свого облікового запису AWS та пристрою.

| Змінна | Призначення |
|---|---|
| `AWS_ACCESS_KEY_ID` | Ідентифікатор ключа доступу AWS для локальної розробки, якщо використовуються статичні облікові дані. |
| `AWS_SECRET_ACCESS_KEY` | Секретний ключ для цього ідентифікатора. Зберігайте його конфіденційно. |
| `AWS_DEFAULT_REGION` | Регіон AWS, у якому розташовані таблиці DynamoDB та ресурси IoT. У прикладі — `eu-central-1` (Франкфурт). |
| `TELEMETRY_TABLE_NAME` | Назва таблиці DynamoDB з телеметрією сенсорів. |
| `EVENTS_TABLE_NAME` | Назва таблиці DynamoDB з подіями пристрою. |
| `DEVICE_ID` | Ідентифікатор пристрою для вибору записів з обох таблиць. Має збігатися зі значенням `device_id` у DynamoDB. |
| `IOT_USER` | Сегмент користувача/пристрою, з якого формується топік команд LED. Має відповідати топіку, який очікують ESP32 та політики AWS IoT. |

Приклад:

```dotenv
AWS_ACCESS_KEY_ID=your_access_key_id
AWS_SECRET_ACCESS_KEY=your_secret_access_key
AWS_DEFAULT_REGION=eu-central-1
TELEMETRY_TABLE_NAME=iot_telemetry
EVENTS_TABLE_NAME=iot_events
DEVICE_ID=your_actual_device_id
IOT_USER=your_topic_user
```

Замініть усі приклади облікових даних та ідентифікаторів реальними значеннями.

Не додавайте `.env` до системи контролю версій і не передавайте його секрети іншим.

Для локальної розробки використовуйте окрему IAM-ідентичність із мінімально необхідними дозволами. Якщо облікові дані вже надані через AWS profile або інше підтримуване джерело AWS credentials, змінні статичних ключів можна не задавати.

На обчислювальних ресурсах AWS надавайте перевагу IAM role замість довготривалих ключів доступу.

## 4. Налаштування AWS і дозволи

### 4.1. Таблиці DynamoDB

Застосунок читає дані з двох окремих таблиць:

- `TELEMETRY_TABLE_NAME` — телеметрія сенсорів.
- `EVENTS_TABLE_NAME` — події пристрою.

Код очікує таку схему ключів кожної таблиці:

- Partition key: `device_id`
- Sort key: `received_at`

`device_id` має збігатися з `DEVICE_ID`.

`received_at` має бути числовою Unix-міткою часу в **мілісекундах**. Для історичних запитів використовується діапазон значень `received_at`, включно з обома межами.

Застосунок виконує операції DynamoDB `Query`. IAM-ідентичності, від якої працює бекенд, потрібен дозвіл `dynamodb:Query` для обох налаштованих таблиць.

Поточний код не потребує `dynamodb:Scan` або дозволів на запис у DynamoDB.

### 4.2. AWS IoT Core

Топік команди LED формується у `app/services/commands_service.py`:

```text
iot-course/{IOT_USER}/commands/led
```

Наприклад, якщо `IOT_USER=StudentName`, топік матиме вигляд:

```text
iot-course/StudentName/commands/led
```

IAM-ідентичності AWS, яку використовує бекенд, потрібен дозвіл `iot:Publish` для ARN відповідного топіка, наприклад:

```text
arn:aws:iot:eu-central-1:<account-id>:topic/iot-course/StudentName/commands/led
```

Зараз для створення клієнта використовується `boto3.client("iot-data")` без явної URL-адреси індивідуального IoT Data Plane endpoint облікового запису.

Якщо публікація команд завершується помилкою endpoint або з’єднання, перевірте IoT Data Plane endpoint для правильного AWS account і регіону. За потреби налаштуйте клієнт у `app/services/commands_service.py`.

Успішна відповідь команди означає, що виклик публікації з боку бекенду завершився успішно. Вона **не підтверджує**, що ESP32 отримала або виконала команду.

Для підтвердження з боку пристрою потрібні телеметрія, подія або інший механізм підтвердження.

## 5. Довідник API

Інтерактивні схеми запитів і відповідей FastAPI доступні у Swagger UI:

`http://127.0.0.1:8000/docs`

### 5.1. Перевірка доступності API та вебсторінка

| Метод і шлях | Параметри / тіло | Поведінка |
|---|---|---|
| `GET /test/health` | Немає | Повертає `{"status":"ok"}`, якщо процес API відповідає. Не перевіряє облікові дані AWS або з’єднання з AWS. |
| `GET /` | Немає | Віддає вбудовану сторінку керування LED з `app/static/led_control.html`. |

### 5.2. Sensors — таблиця телеметрії

Усі ендпоїнти сенсорів читають `TELEMETRY_TABLE_NAME` і фільтрують записи за `DEVICE_ID`.

| Метод і шлях | Параметри | Поведінка |
|---|---|---|
| `GET /sensors/latest` | Немає | Повертає найновіший запис телеметрії для налаштованого пристрою. Якщо запису немає — `404`. |
| `GET /sensors/last-count?count=10` | Обов’язковий `count`, ціле число `>= 1`. | Повертає до `count` найновіших записів телеметрії, відсортованих за `received_at` від нових до старих. |
| `GET /sensors/last-hours?hours=2` | Обов’язковий `hours`, ціле число від `1` до `24`. | Повертає телеметрію за вказану кількість попередніх годин, обчислених від часу сервера. |
| `GET /sensors/history?from_ms=...&to_ms=...` | Обов’язкові `from_ms` і `to_ms`: невід’ємні Unix-мітки часу в мілісекундах; `from_ms <= to_ms`. | Повертає записи телеметрії, для яких `received_at` потрапляє в заданий діапазон, включно з межами. |

#### Який ендпоїнт сенсорів обрати?

- **Останнє значення:** `/sensors/latest` — повертає один найновіший запис.
- **Фіксована кількість записів:** `/sensors/last-count?count=10` — повертає до 10 найновіших записів.
- **Рухомий часовий інтервал:** `/sensors/last-hours?hours=2` — повертає записи за попередні дві години.
- **Точний часовий інтервал:** `/sensors/history?from_ms=...&to_ms=...` — повертає записи в заданому діапазоні міток часу.

Використовуйте `last-count`, коли важлива кількість записів, а не їхній вік.

Використовуйте `last-hours`, коли потрібен рухомий часовий інтервал і немає потреби самостійно обчислювати мітки часу.

Використовуйте `history`, коли клієнт сам визначає часовий діапазон, наприклад за допомогою вибору часу в Grafana.

#### Приклади

Останній запис:

```http
GET http://127.0.0.1:8000/sensors/latest
```

Останні 10 записів:

```http
GET http://127.0.0.1:8000/sensors/last-count?count=10
```

Записи за останні дві години:

```http
GET http://127.0.0.1:8000/sensors/last-hours?hours=2
```

Записи за заданий часовий інтервал:

```http
GET http://127.0.0.1:8000/sensors/history?from_ms=1791741000000&to_ms=1791741600000
```

### 5.3. Events — таблиця подій

Усі ендпоїнти подій читають `EVENTS_TABLE_NAME` і фільтрують записи за `DEVICE_ID`.

| Метод і шлях | Параметри | Поведінка |
|---|---|---|
| `GET /events/latest` | Немає | Повертає найновішу подію. Якщо подій немає — `404`. |
| `GET /events/last-count?count=20` | Обов’язковий `count`, ціле число `>= 1`. | Повертає до вказаної кількості найновіших подій. |
| `GET /events/last-hours?hours=6` | Обов’язковий `hours`, ціле число від `1` до `24`. | Повертає події за вказану кількість попередніх годин, обчислених від часу сервера. |

#### Який ендпоїнт подій обрати?

- **Одна найновіша подія:** `/events/latest`.
- **Фіксована кількість найновіших подій:** `/events/last-count?count=20`.
- **Рухомий часовий інтервал:** `/events/last-hours?hours=6`.
- **Точний часовий інтервал:** `/events/history?from_ms=...&to_ms=...`.

### 5.4. Actuators — команди LED

| Метод і шлях | JSON-тіло | Поведінка |
|---|---|---|
| `POST /actuators/led` | `{"value":"on"}`, `{"value":"off"}` або `{"value":"toggle"}` | Публікує команду LED в AWS IoT Core. Якщо виклик публікації успішний, повертає HTTP `202 Accepted`. |

#### Приклад запиту

```bash
curl -X POST "http://127.0.0.1:8000/actuators/led" \
  -H "Content-Type: application/json" \
  -d '{"value":"toggle"}'
```

Бекенд публікує в налаштований топік таке повідомлення:

```json
{"action":"set","value":"toggle"}
```

Допустимі значення `value` — рядки в нижньому регістрі:

- `on`
- `off`
- `toggle`

Операція `toggle` просить пристрій змінити поточний стан LED. Сам ендпоїнт не зчитує поточний стан.

Якщо виклик публікації успішний, API повертає HTTP `202 Accepted` із відповіддю на кшталт:

```json
{
  "accepted": true,
  "value": "toggle"
}
```

Це підтверджує успішну публікацію з боку бекенду, але не виконання команди пристроєм.

Вбудована сторінка `http://127.0.0.1:8000/` наразі містить кнопки **Led ON** і **Led OFF**. API також приймає `toggle`.

## 6. HTTP-коди та усунення несправностей

| HTTP-код | Значення / що перевірити |
|---|---|
| `200 OK` | Запит виконано успішно. |
| `202 Accepted` | Публікація команди LED успішна; виконання команди пристроєм не підтверджено. |
| `404 Not Found` | Запит не знайшов потрібного найновішого запису сенсора або події. Перевірте наявність даних і відповідність `DEVICE_ID` записам у DynamoDB. |
| `422 Unprocessable Entity` | Параметр запиту або тіло не пройшли перевірку. Перевірте типи параметрів, допустимі діапазони та порядок часових міток. |
| `502 Bad Gateway` | API не змогло виконати операцію AWS. Перевірте credentials, регіон, назви таблиць, схему ключів DynamoDB і дозволи, право IoT-публікації, топік та IoT Data Plane endpoint. |

`GET /test/health` перевіряє лише те, що FastAPI-застосунок відповідає. Успішна відповідь не доводить, що доступ до AWS працює.

## 7. Зауваження щодо безпеки

- Обмежте IAM-дозволи потрібними таблицями DynamoDB і точним топіком команд IoT.
- Не додавайте `.env`, ключі AWS та інші секрети до системи контролю версій.
- Для демонстрації CORS дозволяє всі джерела (`*`). Перед публічним розгортанням замініть це на конкретні довірені адреси frontend.
- Поточна конфігурація CORS дозволяє лише методи `GET` і `POST` та заголовок `Content-Type`.
- У поточному архіві серед тестових маршрутів є лише `/test/health`; окремого ендпоїнта перевірки з’єднання з AWS немає.
